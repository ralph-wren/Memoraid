# 公众号发布 - 修复打开两个页面问题

## 问题描述

用户报告公众号自动发文时会打开两个发文页面，导致重复发布相同内容。

## 问题分析（第一次修复）

通过分析代码和日志，发现问题的根本原因：

1. **Background script** (`handlePublishToWeixin`) 打开公众号首页 `https://mp.weixin.qq.com/`
2. **Content script** (`autoFillContent`) 检测到在首页，调用 `clickArticleButton()` 点击"文章"按钮
3. 点击后会打开一个新的编辑器页面
4. **关键问题**：`chrome.storage.onChanged` 监听器会在所有标签页触发
5. 当首页点击"文章"按钮打开新页面时，新页面的 content script 也会收到 storage 变化事件
6. 导致两个页面（首页和新打开的编辑器页面）都尝试填充内容

## 第一次修复方案

采用两层防护机制：

### 1. sessionStorage 标记机制

在 `autoFillContent` 函数开始时，使用 `sessionStorage` 标记当前标签页是否已经处理过这个任务。

### 2. 提前清除 pending 数据

在首页点击"文章"按钮后，立即清除 `pending_weixin_publish` 数据。

## 问题分析（第二次修复）

第一次修复后，仍然存在问题：

1. 点击"文章"按钮后，页面状态检测返回 `home` 而不是 `editor`
2. 导致代码认为跳转失败，恢复了 pending 数据
3. 实际上页面已经跳转到编辑器，但检测逻辑有问题

通过浏览器调试发现：
- 首页有 3 个包含"文章"文本的元素：`menu-item`（外层）、`menu-content`（中层）、`menu-title`（内层）
- 之前的代码可能点击了外层容器，导致点击不生效或延迟
- 点击后需要等待 URL 变化（从 `home?t=home/index` 变为 `appmsg?t=media/appmsg_edit_v2`）

## 第二次修复方案

### 1. 优化点击逻辑

优先点击最内层的 `menu-title` 元素，并使用多种方法查找：
- 优先查找 `.new-creation__menu-title` 类
- 使用 XPath 精确查找文本为"文章"的元素
- 备用方法：通过类名和文本匹配

### 2. 等待 URL 变化

点击后不再简单等待固定时间，而是：
- 记录点击前的 URL
- 循环检测 URL 是否变化（最多等待 10 秒）
- 只有当 URL 包含 `appmsg` 时才认为跳转成功
- URL 变化后再等待页面加载

### 3. 改进错误处理

- 如果 URL 未变化，返回 `false` 表示点击失败
- 如果 URL 已变化但页面状态检测异常，仍然继续填充（因为 URL 已经正确）

## 问题分析（第三次修复）

第二次修复后，通过手动测试发现：
- `targetElement.click()` 能够成功跳转到编辑器页面 ✅
- 但是会同时打开两个编辑器页面，时间戳相差 1.5 秒

通过分析代码发现根本原因：
1. 首页的 content script 点击"文章"按钮，打开了第一个编辑器页面
2. Background script 的 `handlePublishToWeixin` 函数检测到有编辑器页面存在
3. Background script 执行 `chrome.tabs.reload(tab.id!)` 重新加载编辑器页面
4. 导致打开了第二个编辑器页面

## 第三次修复方案

修改 Background script 的逻辑：
- **移除对编辑器页面的查找和 reload 操作**
- 只查找首页和其他微信页面
- 如果有首页，激活并刷新首页（让 content script 点击"文章"按钮）
- 如果有其他微信页面（包括编辑器），导航到首页重新开始流程
- 这样可以避免 background 和 content script 同时操作导致的冲突

  - 修改首页点击"文章"按钮的逻辑，根据 URL 变化判断成功与否（第二次修复）

- `src/background/index.ts`

## 问题分析（第四次修复 - 最终方案）

第三次修复后，仍然存在问题：
- Content script 点击"文章"按钮后，等待 URL 变化超时（16 秒）
- Content script 认为点击失败，但实际上打开了两个编辑器页面
- 时间戳相差 1.6 秒

**关键发现**：点击"文章"按钮后，**不是在当前标签页跳转，而是打开了一个新的标签页**！

所以：
- Content script 在首页标签页等待 URL 变化 ❌（检测不到）
- 新的编辑器页面在另一个标签页打开 ✅
- Content script 无法检测到新标签页的 URL

**进一步发现**：编辑器 URL 的 token 参数是固定的（从首页 URL 中提取），可以直接构造编辑器 URL。

编辑器 URL 格式：
```
https://mp.weixin.qq.com/cgi-bin/appmsg?t=media/appmsg_edit_v2&action=edit&isNew=1&type=77&createType=0&token={TOKEN}&lang=zh_CN&timestamp={TIMESTAMP}
```

首页 URL 格式：
```
https://mp.weixin.qq.com/cgi-bin/home?t=home/index&lang=zh_CN&token={TOKEN}
```

Token 是用户登录后的固定值，可以从首页 URL 中提取。

## 第四次修复方案（最终方案）

**彻底改变策略**：不再通过首页点击"文章"按钮，而是直接打开编辑器 URL

修改 Background script 的 `handlePublishToWeixin` 函数：

1. 从已有的微信页面 URL 中提取 token
2. 如果没有 token，打开首页获取
3. 构造编辑器 URL
4. 直接打开编辑器 URL（如果已有编辑器页面，导航到新 URL；否则创建新标签页）

优点：
- 避免了点击按钮的复杂性和不确定性
- 不会打开多个页面（因为只有 background 在操作）
- 更快速、更可靠
- Content script 不再需要处理首页点击逻辑

## 最终修改文件

- `src/background/index.ts`
  - 完全重写 `handlePublishToWeixin` 函数的页面打开逻辑（第四次修复）
  - 从微信页面 URL 中提取 token
  - 直接构造并打开编辑器 URL
  - 移除所有首页点击相关的逻辑

## 最终代码改进

```typescript
// 从已有的微信页面 URL 中提取 token
const homeTabs = await chrome.tabs.query({ url: 'https://mp.weixin.qq.com/*' });
let token: string | null = null;

for (const tab of homeTabs) {
  if (tab.url) {
    const match = tab.url.match(/[?&]token=(\d+)/);
    if (match) {
      token = match[1];
      break;
    }
  }
}

// 构造编辑器 URL
const timestamp = Date.now();
const editorUrl = `https://mp.weixin.qq.com/cgi-bin/appmsg?t=media/appmsg_edit_v2&action=edit&isNew=1&type=77&createType=0&token=${token}&lang=zh_CN&timestamp=${timestamp}`;

// 直接打开编辑器 URL
const tab = await chrome.tabs.create({
  url: editorUrl,
  active: true
});
```

## 问题分析（第五次修复 - 彻底解决）

第四次修复后，仍然存在问题：
- 发布一篇文章，先打开公众号首页，然后又打开 3 个编辑页面
- 第一个编辑页面正常执行，另外两个页面什么都没做

**根本原因**：
1. Background script 已经改为直接打开编辑器 URL（第四次修复）✅
2. 但是 Content script 的 `clickArticleButton` 函数仍然存在，仍在处理首页情况 ❌
3. 导致 background 和 content script 同时操作，产生冲突
4. Background 打开 1 个编辑器页面，content script 又尝试点击"文章"按钮（虽然失败了，但触发了多次）

**关键发现**：
- Content script 在首页检测到 pending 数据后，会尝试点击"文章"按钮
- 虽然点击失败（URL 未变化），但是 storage 事件会在多个标签页触发
- 导致打开了多个编辑器页面

## 第五次修复方案（彻底解决）

**策略**：让 content script 完全跳过首页处理，只处理编辑器页面

修改 `src/content/weixin.ts`：
1. 注释掉整个 `clickArticleButton` 函数（不再需要）
2. 在 `autoFillContent` 函数中，如果检测到是首页，直接返回（不处理）
3. 只有在编辑器页面才执行填充逻辑

这样：
- Background script 负责打开编辑器 URL
- Content script 只负责在编辑器页面填充内容
- 两者职责分离，不会冲突
