# 小红书发布上报确认修复 - 缓存问题说明

## 用户反馈
用户反馈：小红书发布后有没有显示 TOKEN，并且标题也变了，之前生成的文章还是正常的。

## 问题分析

### 2. 根本原因
用户遇到的问题很可能是**浏览器缓存**导致的：

1. 浏览器可能还在使用旧版本的扩展代码
2. Chrome 扩展的更新机制：
   - 代码修改后需要重新构建（`npm run build`）
   - 构建后需要在浏览器中重新加载扩展
   - 已经打开的标签页可能仍在使用旧代码

### 3. 为什么"之前生成的文章还是正常的"？
这个说法证实了是缓存问题：
- "之前生成的文章"：使用的是旧版本代码（有 bug）
- "还是正常的"：说明旧版本的数据已经上报成功，只是标题和 token 显示不正确
- 新生成的文章应该会使用新代码，标题和 token 应该正常显示

## 技术细节

### 数据流程（修复后）
1. `autoFillContent` 保存数据到 `sessionStorage`：
   - `memoraid_pending_title`：文章标题
   - `memoraid_token_usage`：Token 消耗数据
   - `memoraid_generated_id`：生成记录 ID

2. `clickPublish` 点击发布按钮：
   - 读取 `sessionStorage` 数据
   - 上报到后端
   - **不清除数据**（关键修改）

3. 页面跳转到 `?published=true`

4. URL 监听器检测到跳转：
   - 读取 `sessionStorage` 数据（此时数据仍然存在）
   - 上报正确的标题和 token 数据
   - **清除 sessionStorage 数据**（在最终上报后）

### 为什么有两次上报？
小红书的发布流程比较特殊：
1. 点击"发布"按钮后，页面不会立即跳转
2. 需要等待一段时间（服务器处理）
3. 然后页面才会跳转到 `?published=true`

因此需要两个上报点：
- `clickPublish`：立即上报，让用户知道已经点击了发布
- URL 监听器：最终上报，确认发布成功

但只有 URL 监听器的上报才应该清除数据，因为这是最终的确认。

## 注意事项

### 1. Chrome 扩展缓存机制
- Chrome 扩展的 content script 会被缓存
- 修改代码后必须重新加载扩展
- 已打开的标签页可能仍使用旧代码
- 建议关闭所有相关标签页后再测试

### 2. sessionStorage 的生命周期
- `sessionStorage` 在标签页关闭后会被清除
- 页面刷新后数据仍然保留
- 不同标签页的 `sessionStorage` 是独立的

### 3. 调试建议
如果仍然遇到问题，可以：
1. 打开浏览器开发者工具（F12）
2. 切换到 Console 标签
3. 查看日志输出：
   ```
   [Xiaohongshu] 准备上报文章: { title, url, generatedId, hasTokenUsage }
   [Xiaohongshu URL Monitor] 准备上报文章: { title, url, generatedId, hasTokenUsage }
   ```
4. 检查 Application > Session Storage > sessionStorage
5. 确认数据是否正确保存和清除
