# 定时任务 - 使用后端数据库存储避免配置覆盖问题

## 问题描述

之前定时任务的配置存储在 `chrome.storage.sync` 中，当任务执行时会更新任务状态（lastRunTime、lastRunStatus、lastRunError）。由于更新逻辑是"读取完整配置 → 修改 → 保存"，如果用户在任务执行期间修改了配置，保存操作会覆盖用户的修改。

## 已完成的工作

### 1. 后端数据库表 ✅

创建了 `scheduled_tasks` 表存储定时任务配置，包含所有必要字段。

### 2. 后端 API ✅

新增了完整的 CRUD API：
- `GET /api/scheduled-tasks` - 获取用户的所有定时任务
- `POST /api/scheduled-tasks` - 创建新的定时任务
- `PUT /api/scheduled-tasks/:id` - 更新指定的定时任务
- `DELETE /api/scheduled-tasks/:id` - 删除指定的定时任务
- `PATCH /api/scheduled-tasks/:id/status` - 更新任务执行状态（供调度器调用）

### 3. 调度器状态更新 ✅

修改了 `src/background/scheduler.ts` 中的 `updateTaskStatus` 函数，改为调用后端 API 更新状态，避免覆盖用户配置。

### 4. 后端部署 ✅

后端服务已成功部署到 Cloudflare Workers。

## 下一步工作

### 前端 UI 改造（待完成）

需要修改 `src/components/ScheduleSettings.tsx`，实现以下功能：

1. **从后端加载任务**
   - 组件挂载时调用 `GET /api/scheduled-tasks` 加载任务列表

2. **添加保存按钮**
   - 每个任务添加"保存"按钮

   - 点击保存按钮调用 `POST` 或 `PUT` API

3. **删除任务**
   - 调用 `DELETE /api/scheduled-tasks/:id` API

4. **状态管理**
   - 使用本地 state 管理任务列表
   - 区分"未保存"和"已保存"状态
   - 显示保存中的 loading 状态

## 核心改进

1. **避免配置覆盖**：任务状态更新和配置修改分离，互不影响
2. **数据持久化**：使用后端数据库存储，比 chrome.storage 更可靠
3. **支持多设备同步**：后端存储天然支持跨设备访问
4. **更好的并发控制**：数据库级别的事务保证数据一致性

## 临时解决方案

当前版本已经解决了最核心的问题：
- 调度器更新任务状态时不再覆盖用户配置
- 状态更新通过独立的 API 接口完成

用户可以继续使用现有的 UI，虽然还是从 chrome.storage 读写，但至少不会被调度器覆盖了。
